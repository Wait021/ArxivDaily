### [OmniEdu: Open Foundation Models for Learning and Teaching](https://arxiv.org/abs/2609.23088)

`2609.23088` · 2026-09-19 · [PDF](https://arxiv.org/pdf/2609.23088)

# OmniEdu 深度解读

这篇论文做了一个 K–12 教育领域的开源基础模型族（4B/9B/27B），但它真正的核心贡献不在模型，而在**“能力导向的指令数据工程”**——一套从 134 万原始样本筛选到 7 万高质量样本的可复现流水线，以及“内容与行为解耦”的训练数据组织思想。以下按你的框架展开。

---

## 🎯 研究动机与要解决的问题

**核心命题：教育模型不能只看答案正确率。** 一个合格的教育助手必须同时协调三件事：*what to teach*（学科知识）、*where the learner is*（学习者在课程结构中的位置与错误诊断）、*how to respond*（选择合适的教学干预，如提示、追问、先修复习或直接讲解）。

作者指出现有工作的三个缺口：

1. **能力割裂**：现有教育 LLM 要么专精解题（Confucius3-Math），要么专精辅导对话，没有一个开源模型族的训练目标和评测协议覆盖完整的“学习–教学闭环”；
2. **数据组织方式有缺陷**：教育指令数据高度异构（一个短答案、一条课程关系、一个误概念诊断、一段辅导对话，监督的是完全不同的行为），仅按“来源/学科”混合会让模型学到混乱的响应策略，且容易过度代表简单冗余样本；
3. **前沿系统闭源**：LearnLM、ChatGPT Study Mode、Khanmigo 等依赖产品级编排，能力难以复现和扩展。

因此论文把问题重新表述为一个**数据设计问题**：不是收集更多教育数据，而是构造一个“每个样本都有明确能力目标 + 教学上恰当的响应行为”的训练混合物。

---

## 🔧 方法（技术路线、关键设计、为什么这样设计）

### 1. 四能力分类法

教育数据被按**目标行为**而非来源划分为四类：

| 能力 | 内容 | 最终数据占比 |
|---|---|---|
| Subject competence | K–12 各科解题与解释 | 45.5%（31,855 例） |
| Pedagogical action & scaffolding | 选择并执行教学干预（提示/追问/先修复习/讲解） | 20.3%（14,226 例） |
| Curriculum grounding | 知识点对齐、年级、难度、先修关系、课程定位 | 13.4%（9,381 例） |
| Diagnostic reasoning | 从学生作答中识别错误与误概念、推断缺失先修 | 7.8%（5,489 例） |

另有 12.9%（9,048 例）通用指令数据（DataFlow-Instruct-10K、Tulu-3、MathV360K）用于保住通用指令跟随、多语言、拒答与图文推理能力。

### 2. 六阶段数据流水线（1.34M → 69,999）

```
≈1.34M → 870,711 → 440,100 → 121,318 → 60,951 (+9,048 通用) → 69,999 例 / 15.96M 监督token
```

- **① 来源收集**：100+ 数据集/教育资源；
- **② 确定性清洗 + 评测去污染**：统一格式、去重、必填字段校验、可验证答案与参考答案的一致性检查、多模态图文对齐校验、许可证过滤、**与最终评测集的重叠去除**；
- **③ LLM 语义审计与重写**（Qwen3.5-122B）：每例打 0–100 可用性分并标注 keep/rewrite/remove（≥85 保留、50–84 送修、<50 丢弃）。审计标准**按能力定制**：学科数据查答案正确性与解释一致性；诊断数据查“指认的错误是否真的被学生作答支撑”；教学数据额外查**“是否过早泄漏最终答案”**（脚手架质量的核心）。重写时**只修监督信号、不动输入**，修完再审；
- **④ 初步多样性压缩 + 细粒度打分**：对冗余严重的源（如 RACE 60,180→5,000）用 **BGE-M3 嵌入上的 k-center greedy** 选语义多样子集（而非随机采样）；再用 GPT-5.6 按**任务特定的多维 rubric** 打 1–5 分，全维度 ≥3、关键维度（正确性/有效性/grounding）≥4 才保留；
- **⑤ Token 预算多样性选择**：这是很聪明的一笔——**按“监督响应 token 数”而非“样本数”给每个细粒度任务桶分配预算**，因为一段长辅导对话的贡献可能比一个短答案大一个数量级。桶内仍用 k-center greedy 贪心选满预算为止；
- **⑥ 教学指令分配**：借鉴 LearnLM 的 *pedagogical instruction following*，给每个样本按任务桶挂上 **20 个系统指令模板之一**（解题式、阅读理解式、诊断纠错式、苏格拉底式、辅导对话式……），明确告诉模型该样本期望的响应行为。**原始 user/assistant 内容不变**。

### 3. 为什么这样设计（论文的隐含逻辑）

- **内容与行为解耦**：同一段学生错解，可以监督出“给出正确答案”或“不给答案、给提示”两种冲突行为。单条通用系统指令会把二者混在一起；显式的任务级系统指令让一个模型学到多种行为，且**推理时可通过切换指令切换行为**；
- **Token 预算而非样本预算**：保证长对话/长解释类任务不会被短答案类在 token 层面淹没；
- **确定性规则先、昂贵 LLM 后**：先用免费规则砍掉 35%，再花大模型预算做语义质控，成本结构合理；
- **训练配置**：Qwen3.5-4B/9B-Base 与 Qwen3.8-27B，LLaMA-Factory 全参 SFT，lr=5e-6、3 epochs、32K 上下文、ZeRO-3、bf16。

## 📊 实验与结果

**设置**：3 个尺度 ×（base vs tuned）配对对比；基线包括开源教育模型和 5 个前沿专有模型（GPT-5.4/5.6-Sol、Claude-Opus-5、GLM-5.3、Kimi-K3）。

**主要数字（OmniEdu-27B vs 对应 base）：**

| 维度 | 基准 | Base → Tuned | 相对位置 |
|---|---|---|---|
| 课程定位 | K12-Bench EM/F1 | 52.11/73.48 → **63.12/76.69** | 全场第一 |
| | MathFish | 83.54 → **85.89** | 第一 |
| | EDUMATH MaC | 70.60 → **86.95** | 第二（仅次于 Kimi-K3 的 90.00） |
| 解题 | GAOKAO-Bench Full | 91.55 → 94.87 | 专有模型仍略高（Claude 97.22） |
| | EXAMS-V | 68.65 → 69.52；4B 从 44.69 → 57.62 | 远不及 Kimi-K3 的 87.29 |
| | MDK12-Bench | 46.04 → **57.76**（开放题 62.08→78.77） | 第二 |
| 教学 | MathTutorBench Scaffold | 57.16 → **78.74**（4B +55.4、9B +61.3） | 仅次 Claude-Opus-5 |
| | TutorBench | 58.58 → **59.42** | 第二（Kimi-K3 63.65） |
| | LongTutor Teaching / Evidence | 2.74 → **3.02** / 36.80 → 78.20 | Teaching 第一 |
| 通用 | IFEval / GPQA / MMMU-Pro | 全部提升（MMMU-Pro 64.97→67.98） | 无灾难性遗忘 |

**关键发现**：
1. 三个教育维度在**所有尺度**上一致提升，其中**脚手架式教学和对学生历史证据的利用提升最大**（Scaffold win rate +20~60 点）——正是“行为监督”最缺、也最依赖显式指令的部分，侧面验证了数据设计的价值；
2. 基座本身不弱（Qwen3.8-27B 在解题上已很强），提升主要来自课程推理、错误敏感教学这些“非答案”能力；
3. 通用能力不降反升，说明 12.9% 通用数据 + 高质量小数据 SFT 的代价可控。

## ⚠️ 局限与开放问题

1. **无关键消融**：论文主张"capability-balanced"有效，但**没有做能力桶配比消融、系统指令分配消融、token 预算 vs 样本预算的对照**，也没有 DPO/RL 阶段对比，核心主张的因果链只有 base vs tuned 一个对照点；
2. **诊断能力仍是最短板**：诊断类数据只占 7.8%，LongTutor 知识状态诊断准确率最高也仅 54.04%——数据配比与能力上限的对应关系很明显，但论文没有深入分析；
3. **小尺度上出现能力回退**：附录 Table 7 中 4B 模型 GAOKAO 中文从 90.89% **跌到 59.30%**（9B/27B 反而大升），TutorBench UC1 上 4B 也下降——能力平衡在 4B 上没有调好，提示小模型的多行为学习存在 trade-off；
4. **专有模型在部分考试评测仍明显领先**（EXAMS-V 上 Kimi-K3 87.29 vs 69.52）；反过来 GPT-5.4 在 EXAMS-V 只有 35.66%，也说明**评测协议对不同模型的格式适配并不公平**，跨组对比需谨慎；
5. **学科覆盖偏数学/理科**：主体能力桶里写作/人文类源极少（ELLIPSE 348、ASAP 331），"K–12 全科"的说法略强；
6. **完全没有涉及 agent、工具调用、多轮规划**：模型是纯 SFT 的行为条件模型，教学中“何时该检索课程资源、何时调用外部工具”这类 agentic 决策不在本文范围内；
7. 去污染只针对自身评测集，未讨论更广义的 benchmark 泄漏；另有些写作瑕疵（如 27B 基座写作 "Qwen3.8-27B"，与 4B/9B 的 "Qwen3.5" 不一致）。

## 💡 对我的研究的启发

这篇论文领域上与翻译无关，但它的**数据方法论几乎可以整体移植到“翻译 LLM/翻译 Agent 的底座训练”**上。具体到你的 PPT/XML 富结构文档翻译智能体：

1. **把“能力分类法”搬到翻译数据上**。OmniEdu 最核心的动作是先定义行为分类再收数据。你可以为富结构文档翻译定义对称的四能力：(a) **翻译能力**（文本节点质量）；(b) **结构 grounding**（XML tag/属性/占位符/CDATA/注释的识别与保护规则、PPT 中 text frame/master/layout 的角色感知）；(c) **翻译诊断**（检测 tag 泄漏进译文、占位符丢失、数字/URL 变形、术语不一致、漏译节点——对应用户场景里最痛的结构破损）；(d) **修复与策略行动**（局部重译、tag 回填、触发翻译记忆/术语库检索）。按这个 taxonomy 重组你的 SFT/评价数据，能直接解决“按语料来源混合导致行为混乱”的问题。

2. **“内容–行为解耦 + 20 个系统指令模板”→ 你的 Agent 路由层**。这是对翻译 Agent 最直接的一条启发：不要为“保守直译 / 本地化改写 / 术语强制 / 结构保真优先 / 只诊断不重译”分别维护模型或 prompt hack，而是**在训练时就给同类数据挂不同的行为系统指令**（“严格保结构模式：仅翻译文本节点，所有标记原样输出”、"字幕口语化模式”、“诊断模式：输出错误报告”）——让一个底座学到多策略，Agent 控制器在推理时按文档类型/质量反馈切换指令。这比推理时临时换 prompt 稳健得多，也正好是你 agent 层与模型层的接缝设计。

3. **确定性规则 + LLM 审计的双层质控，天然适合 XML/PPT 数据**。你的场景比教育场景更幸运：结构文档有大量**可确定性校验**的信号（XML 良构性、tag 集合差集为空、占位符/变量集合差集为空、数字与 URL 逐字符保持、双语文本长度比区间、pptx 解包后关系完整性）。完全可复刻它的漏斗：规则层先砍 → LLM 语义审计（译文保真/术语/风格，0–100 分 + rewrite 修复）→ 任务特定 rubric 打分（关键维度阈值 4）→ 多样性选择。论文的审计 prompt 和 20 个模板都随数据开源，可以直接改写成翻译版。

4. **Token 预算的多样性选择，解决长文档配比问题**。XML 全文档翻译样本与句段级样本的响应 token 差数个数量级——按样本数配比会让长文档上下文能力（跨节点术语一致、指代消解）被句段样本淹没。**按监督 token 给“句段级 / 元素级 / 全文档级 / 诊断报告级”任务桶分配预算**，桶内用 k-center greedy（BGE-M3）保证体裁覆盖（技术/法律/营销/学术），是可直接落地的做法。

5. **评测的三维度组织方式**。它按“课程定位 / 解题 / 教学”三组报告而非单一分数；你同样可以按“**结构保真子基准**（tag precision/recall、well-formedness 率、占位符存活率）/ **翻译质量** / **Agent 流程能力**（工具调用正确率、错误恢复、检索命中率）”三组建评测，并且像 LongTutor 那样把“诊断”单独列指标——你大概率也会发现**诊断（critic）是数据最稀缺、能力最弱的一环**，需要刻意加配比。

6. **一个明确的差异化机会**：OmniEdu 是纯 SFT、零 agent 成分。把它的“能力导向数据 + 行为指令”思想扩展到**工具使用型翻译 Agent**——即把“何时调用术语库/翻译记忆/验证器/重译循环”也作为一种被显式监督的行为类别混入数据——是它没做、而你的方向正好补上的增量创新点。此外它证明了 **~7 万样本 / 16M token 就能在专项能力上追平前沿专有模型**，对资源有限的翻译专用模型训练是个很强的成本信号。

7. **反面教训也要记**：4B 上的中文科目大幅回退说明小模型做多行为学习时，**某个能力桶的数据压缩（如中文阅读语料被 k-center 压掉）会伤及无辜能力**——你在压缩冗余平行语料时，要按“语言 × 体裁 × 结构类型”监控副作用，而不是只看桶内多样性。

### [Realtime-Venus: A full-duplex interaction system with asynchronous delegation](https://arxiv.org/abs/2609.13814)

`2609.13814` · 2026-09-12 · [PDF](https://arxiv.org/pdf/2609.13814)

# Realtime-Venus 深度解读

**一句话概括**：蚂蚁集团 + 清华提出的“主动式全双工交互系统”，核心是把**实时会话前端（两个分别训练的 9B 模型：Omni 音视频版 / Audio 纯语音版）**与**异步任务委托后台**放在同一条共享因果时间轴上：前台边看边听边说，后台边查边算，工具结果通过“私有通道”回流进正在进行的对话。基座为 MiniCPM-o 4.5。

---

## 🎯 研究动机与要解决的问题

论文抓住的核心矛盾是：**同一会话内，不同计算任务运行在截然不同的时间尺度上**。

1. **异步委托的“时序错位”问题**：一个后台任务（查资料、调工具）需要一个*稳定的*请求与证据记录才能可靠执行；但任务结果返回时，对话可能已经变了（用户改口、追问、换话题）。如何协调“任务捕获”与“会话式结果交付”，是全文的纲领性问题。
2. **全双工 ≠ “能被打断”**：重叠语音的语义功能各异——停顿/噪音（应继续听）、backchannel（“嗯”“对”，不抢话轮，应继续说）、真打断（需停止/修复/重定向当前响应）。基于 VAD 的二元中断判断太粗糙，需要**语义级**的轮次控制。
3. **主动响应**：无显式请求时也要能基于视觉事件发起说话（例：“裁判吹哨时提醒我”）。
4. **长会话上下文溢出**：小时级视频超出基座的 rolling context window，历史信息不可达。

**现有工作的缺口**：Moshi / Qwen2.5-Omni / Qwen3-Omni 有流式语音但无“流内”异步工具调用；MoshiRAG、DuplexOmni、GPT-Realtime 探索了异步检索/思考层，但“证据边界固定 → 执行 → 结果会话式重入”的完整闭环未被系统化。作者声称 Realtime-Venus-Omni 是**首个在维持视频交互的同时支持异步后端调用的全双工 omni 模型**。

---

## 🔧 方法

### (1) 双循环架构
- **交互环（前台，延迟敏感）**：连续感知、更新会话状态、控制听/说/让权、原生流式语音输出。
- **能力环（后台，按需、长时延）**：前端发出自然语言委托请求 → 宿主隐藏该 span、在请求边界截取上下文快照 → 创建工作项 → Harness 路由到注册能力异步执行 → 结果润色为口语回复 → 私有通道回流原会话 → 前端择时说出。
- **关键责任切分**：*Harness 决定“说什么”（内容与措辞），前端决定“何时说”（会话时机）*——与两者的延迟特性精确匹配。

### (2) 前端模型（9B，改造 MiniCPM-o 4.5 的 Omni-Flow）
SigLIP2（视觉）+ Whisper-Medium（音频）→ 投影 → Qwen3-8B 主干（Thinker）→ 文本 + 隐状态条件化 S3 语音 token → 流式 flow-matching 解码器（Talker）。Audio 版仅去掉视觉分支。以 **1 秒为一个 unit**：每个 unit 先预测 `<|listen|>` / `<|speak|>`；说话 unit 内生成文本并条件化对齐的语音 token（约 25 token/s）；`<|chunk_eos|>` 关闭语音块，`<|turn_eos|>` 关闭轮次。chunk 化调度使“感知与说话并发、**未说出口的续写可修订**”成为可能。

### (3) 统一流序列化（全文最核心的设计）
- 三条逻辑流——**用户流**（时间对齐的感知特征，说话期间保持活跃）、**助手流**（前台文本 + S3 语音 token + 可选纯文本委托指令）、**后台流**（异步纯文本）——对齐到共享会话时钟，交错为单一 token 流。
- 新增 4 个 token：`<delegate>` `</delegate>` `<backend>` `</backend>`（加入 tokenizer、输入 embedding 和 LM head）。委托 span 是**自包含的自然语言任务**，对用户隐藏（不显示、不朗读）；结果以 `<backend>` span 在可用 chunk 边界插入**用户流**，作为“**外部上下文而非预测目标**”（该 span 本身不计 loss，助手对其的复述才被监督——见附录 B.2）。
- 说话期间的**文本排放按播放进度自适应调速**（公式 2：选择 n 使得已调度语音结束时间 + 前 n 个候选 token 的估计时长最接近当前 chunk 边界）——语音滞后就少发文本，播放有余量就多发。训练时按起始时间把文本/S3 token 分配进 chunk，学到“历史依赖的交错”而非固定文本-语音比例。
- **为什么这样设计**：统一时间轴让“何时响应、何时委托、结果何时重入”成为同一策略下的联合决策，而不是外挂规则系统。

### (4) 全双工的形式化
联合策略分解：p(O₁:K|U,B) = Π p_θ(c_k, Y_k, D_k | U≤k, B≤k, O<k) · p_φ(S_k | H≤k, Y≤k, S<k)。声学生成放在 LLM 之外，但轮次控制、文本、委托共享同一语义表示——因此**声学上相似的重叠语音会依会话角色产生不同续写**。打断进一步细分为三种语义动作：**stop/reject**（关轮、丢弃未说余段）、**repair/update**（吸收新证据、重生成陈旧续写）、**redirect/follow-up**（挂起当前计划、转交控制权）；已播放音频不变，只改未说部分。

### (5) 免训练长视频记忆
- **存档门控**：借鉴 AdaCodec 的预测编码思想，用块级运动补偿的残差 + 运动代价估计相邻采样帧的视觉变化，决定是否入长期记忆；加局部变化保护与最大连续丢弃约束防丢短事件。只影响长期存档，不影响短期上下文。
- **检索**：MaxSim 式 token 级最大余弦相似度，用得分的中位绝对偏差（MAD）加权（强调跨帧得分差异大的 query token）聚合为帧相关分；再按 MMR 的“相关性 + 新颖性”原则选帧。
- **重组装**：检索帧 + 其时间邻接音频、区间去重合并，按时间顺序与近期窗口、当前查询拼成上下文。全程零训练、与微调后的对话策略解耦。

### (6) Realtime-Venus-Harness（异步执行框架）
- **Capture（因果任务捕获）**：协议校验 + 任务身份检查（一个请求至多一个工作项）；以 κᵢ =（开 token 时间戳 Tᵢ, 当时最新输入序列）为界，在回看视界 Δ 内做快照 Xᵢ = Snap(B_σ; κᵢ, Δ)；时间戳/序列栅栏把证据限制在 Tᵢ 之前可得的观测，此后的新观测**不能改变** Xᵢ——**证据边界在请求创建时冻结，与提交时间无关**。
- **Dispatch（可扩展能力执行）**：注册表含 γ_mm（多模态感知问答）、γ_gen（通用多步规划）+ 可注册技能；路由器基于能力契约与**紧凑证据摘要**（不看原始媒体）做一次模型决策选出能力与参数；schema 校验拒绝非法选择；所有路径产出统一格式的归一化结果。新技能只需提供契约 + 执行器。
- **Return（会话式结果重入）**：适配器对执行结果做纯文本润色、去除保留控制 token、包成单条 `<backend>` 消息回流原会话；在某 chunk 边界被 **admit** 为背景输入——**admit ≠ 说出**，前端用当前交互状态调度何时开口。
- **生命周期**：QUEUED→RUNNING→COMPLETED→DELIVERING→DELIVERED（+FAILED）；DELIVERED 需前端生成完成且每个语音 chunk 获播放确认。请求携带**新鲜度截止**：超期结果在终态构造时判 stale、排除出重入。状态记录为“异常发生在哪个阶段、如何处理”提供依据。
- **为什么用 NL 委托而非工具 schema**：前端不必编码后端专属的工具调用格式，保持通用性；schema 复杂度吸收在 Harness 契约层；复合请求可按语义顺序触发多次调用；说话期间到来的新请求可不开轮直接派发。

### (7) 数据管线（双目标耦合）
三段式：①**场景与交互规划**（结构化种子→事件级计划：语义推进、说话人/受话人、话轮所有权、每个事件“保持或改变当前意图”；覆盖日常/检索/协作/决策/服务/多方）；②**副语言与声学实现**（犹豫、填充停顿、自纠、不完整句、笑、呼吸；场景匹配的背景说话人与环境音；中文、英文、码切换）；③**时间对齐与物化**（音/视/文/系统动作映射到单调会话时钟；同一轨迹物化为 audio-only 或 video 两种训练数据）。每条轨迹耦合两个监督目标：**duplex target**（立即会话动作：继续说/等待/让权/停排队音频/修订——按会话意义而非声学重叠选择）与 **delegation target**（计算处理：本地直答/调能力/调工具；保留/取消/修订/有界重试/降级回退），由“事件是否改变用户意图”链接二者。规模：**280 万+ 样本、9 类**（视频侧约 70%：AV 理解 936k、视觉主动双工 454k、omni 主动双工 201k、speech-in 双工 315k、委托 95k；音频侧约 30%：音频理解 470k、口语 QA 205k、纯语音双工 100k、委托 90k）；离线理解 56%、主动双工 37%、委托 6%；约 72,200 会话、约 1,600 小时对齐音频（中英各约 36,100 会话）。

### (8) 训练配方
单次后训练混合“离线理解 + 主动双工 + 委托”三类数据；**稀疏监督**（仅响应 span 计 loss）；**按样本归一化**（每样本加权 loss 除以其监督权重，防止贡献随 token 数膨胀）；长答案的 LM-head 交叉熵**分 chunk 重算**以限制激活内存；**只更新 Thinker，声学解码器冻结**。

### [RRSI: Regularized Recursive Self-Improvement of Agent Harnesses](https://arxiv.org/abs/2609.24972)

`2609.24972` · 2026-09-21 · [PDF](https://arxiv.org/pdf/2609.24972)

# RRSI 深度解读：给 Agent Harness 的递归自我改进加上“正则化”

> 一句话概括：把“用 LLM 自动迭代优化 agent 的 prompt/控制流/工具/记忆”视为一种系统级递归自我改进（RSI），指出这种进化会像训练一样**过拟合到 evolve 集**（背题、追噪声、堆复杂度），然后把经典的 L0/L1/L2 正则化思想“翻译”成对**提议和选择两个环节的约束**，让留下来的 harness 改动是可复用机制而非基准特解。

---

## 🎯 研究动机与要解决的问题

**背景判断**：现代 LLM agent = 冻结骨干模型 π + harness H（提示词、控制流、工具接口、记忆/技能文件、上下文管理）。同一个模型“是否先读对文件再编辑、能否从失败命令恢复、如何管理工作上下文、是否把结果写进交付物”，全由 harness 决定。业界很多进展其实来自 harness 工程而非新权重，但这一步依赖人工读失败轨迹、手工调 scaffold——进度受限于工程师能读多少轨迹。

**自动化趋势与陷阱**：近期方法（Meta-Harness、AHE、TTHE、HarnessX 等）用 LLM 根据任务反馈迭代提出 harness 的组件级修改、按分数选择保留——这实质上是 agent 系统层面的 RSI。但作者指出一个关键风险：**evolve 集被自适应地反复复用**（第 t 轮的候选由同一批任务在早前轮次的测量结果诱导提出），这在统计上正是 adaptive data analysis 中的 holdout 复用问题（引用 Dwork et al., 2015），会导致 evolve 集分数虚高而泛化崩塌。

论文把过拟合分解为三种耦合的失败模式，这个分类很有分析价值：

1. **Benchmark-specific fitting**：把 evolve 基准的任务名、实体、答案等特异模式直接编码进 harness（即“背题”）；
2. **Noise chasing**：有限次随机评估的噪声被当作真实信号，“随机赢家”被固化为永久状态；
3. **Complexity accumulation**：靠堆上下文、加步骤、加测试时算力抬分，而不是改进底层机制。

图 1 的实证很扎心：在 agentic workspace 基准上，先前方法的 evolve 集增益几乎全部蒸发，AHE、TTHE 的 OOD 分数甚至**低于从未进化的初始 harness H0**——进化了个寂寞甚至负收益。

**设计目标**：不缩小可编辑空间（prompts/控制流/工具/记忆/子代理全都能改），而是**正则化搜索在这个空间中的移动方式**。

---

## 🔧 方法（技术路线与设计理由）

形式化很干净：agent A=(π, H)，π 冻结；在 evolve 集上跑轨迹得经验分数 Ŝ 与 policy-token 成本 Ĉ；标准进化循环是“执行→反馈→提议候选→按 Ŝ 选 argmax"。RRSI 在**提议分布**和**选择准则**两侧各加约束，全部是**非补偿性**的（先过筛才有资格按分数竞争）。

### 提议侧：控制搜索容量怎么花

| 机制 | 做法 | 为什么这样设计 |
|---|---|---|
| **L0 式退火编辑预算** | 一个候选能捆绑的“可独立归因原子编辑”数 ≤ b_t，按余弦调度从 b_max 退火到 b_min | 无约束 proposer 会把一堆不相关改动打包，容量过大既能拟合 evolve 集特异性质、又无法归因是哪个改动起效；早期允许多编辑组合去**发现新机制**，后期稀疏化保证**可归因性** |
| **证据感知信用分配** | 记录每个被评估候选的（组件、假设、diff、ΔS、ΔC、是否接受）完整历史，proposer 后续轮次以此为条件 | 被拒机制成为“负证据”，避免反复花容量验证已被证伪的假设；且随着预算退火到 1，测量自然变得可归因——两个机制互相强化 |
| **结构化探索** | 组件词汇表 K={prompt, control_flow, config, output_plumbing, context_mgmt, client_tool, skill, memory, subagent}；w 轮内进度不超过噪声带 δ 判定 stall，此时预留预算给从未动过的组件 | 防止搜索塌缩到“反复改 prompt、从不碰结构机制”的窄家族，类似熵/多样性正则 |

### 选择侧：控制哪些增益能成为永久状态

| 机制 | 做法 | 为什么这样设计 |
|---|---|---|
| **Leakage 筛查（评估前）** | critic 读 diff，拒绝编码任务名/实体名/任务特定取值/答案/基准特定逻辑、以及添加惰性机制的编辑 | 关键细节：**筛查在评估之前**——泄漏候选永远不会拿到那个虚高的、会在后续轮次吸引搜索的分数 |
| **稳定性感知接受（噪声地板）** | 进化前对不变的 H0 反复评估，标定经验噪声带 δ；候选须满足 Ŝ(H′) ≥ S★ − δ | 防止搜索通过一串“每个都小到像噪声”的回退**一路下山**；这是对重复随机评估的保守化 |
| **L2 式复杂度感知接受** | 对 ΔS > δ 的候选要求 ΔC ≤ β0 + β1·ΔS；带内（ΔS≤δ）用整形规则 w_s·ΔS − w_c·ΔC + w_n·ν > 0（ν = 从未进入获胜编辑的结构性组件类型数） | 额外推理成本必须被可测增益证成；带内分支防止把小波动当证据（coding 实例 w_s=0，带内涨分本身不能入选） |
| **L1 式结构剪枝** | 滑动窗口内被行使过但无严格正增益的组件 → 报告为 proposer 的删除目标 | 机制必须持续“挣得”自己的位置，防止 score-only 进化只加不减、harness 越长越肥 |

作者很诚实地声明：L0/L1/L2 只是**角色类比**（更新基数约束 / 结构稀疏化 / 整体收缩），不是真的在优化范数惩罚目标。附录给出了完整的轮级算法、超参表（如 coding 域 δ=0.017 ≈ 178 次试验中 3 次通过、β1=44.5 意为每多过一题允许 25% token 增量），以及工程设计域的额外守卫（有效输出率降 >0.03 直接拒）。

## 📊 实验与结果

**设置**：8 基准 3 域，每域只在**一个**套件上进化，其余全部原封不动测迁移。策略冻结 Claude Opus 4.8（proposer/critic 同模型），所有基线共享 H0、evolve 集、候选预算。

| 域 | Evolve 集 | 结果 | OOD 基准 | 结果 |
|---|---|---|---|---|
| Coding | Terminal-Bench 2.1 | 74.2→80.2（+6.0） | SWE-bench Verified | 82.0→83.8（+1.8） |
| Agentic workspace | Harvey LAB | 89.4→90.5（仅 +1.1） | JobBench / GDPval / APEX | 36.0→40.7（**+4.7**）/ 48.8→52.3 / 34.2→37.9；OOD 均值 39.7→**43.6** |
| 工程设计 | EngDesign | +4.9 | Frontier-Eng | +4.3 Medal（相对 +24.3%） |

**与基线的对比（核心卖点）**：四个基线在 evolve 集上都涨得不错，但 OOD 排名倒挂——最强的 Meta-Harness 在 OOD 仅 +0.9，HarnessX ≈ 0，AHE/TTHE **低于 H0**（TTHE −1.7）。RRSI 的 evolve 增益是所有进化方法中**最小的**（90.5 vs 无正则的 92.8），却是唯一 OOD 均值超过 H0 一分以上的——这正是正则化“设计出来要做的交换”。

**消融**：去掉任一组正则 → evolve 分涨、OOD 跌（去 acceptance 侧：91.5 / OOD 41.0 / token 涨一半；去 proposal 侧：90.7 / 41.9）；全去掉 → 92.8 / 40.3 / 3.80M tokens。两组正则各有贡献、组合最强。

**成本**：RRSI 最终 harness 每试验 2.42M tokens、26.3 步，比无正则进化（3.80M）省约 1/3；AHE 花得多 58% 还 OOD 低 4.4 分。没有任何进化 harness 比 H0（1.56M）便宜——进化确实用测试时算力买了部分增益，**预算规则决定买多少**。

**稳健性**：(1) 换骨干：Gemini 3.5 Flash 下 TB 64.6→78.7（+14.1，全文最大 evolve 增益），SWE 仍 +2.2；(2) **跨模型迁移**：用 Gemini 3.5 Flash 进化出的 harness 给从未参与搜索的 Gemini 3.1 Flash Lite 用，TB 11.2→14.6（相对 +30.4%）——机制不绑定搜索时的能力水平；(3) 确定性判分域（EngDesign/Frontier-Eng 用冻结模拟器）排除了“学会讨好 judge”的解释。

**案例研究值得细读**：R0-A（提交前验证审计+长任务非阻塞轮询，+3.93，接受）vs R0-B（类似机制，+1.69 但 +26.1% 成本，被成本规则拒）；R8-B（pin 原任务指令进完成门，省 13.6% 成本但 −2.81 分，被地板拒）；Eng R2（对复发性 "workdir must be an existing directory" 工具错误的恢复提示，+6 题仅 +1.6% token，接受）——展示了“分数、成本、稳定性”三方共同裁决的具体形态。

## ⚠️ 局限与开放问题

**作者自述**：仅覆盖骨干冻结的 harness 级 RSI（不涉及权重更新）；依赖有限 evolve 集和多个超参；对反馈质量与搜索预算敏感；跨架构/工具生态/更长程自改进的泛化待验证。

**我认为值得追问的**：

1. **分布内增益被主动压小**（最强策略下 Harvey 仅 +1.1）。如果你只关心单一分布，无正则进化分数更高。正则强度如何随任务多样性和 evolve 集大小自适应，是悬而未决的问题。
2. **理论缺口**：L0/L1/L2 是定性类比，没有泛化界；与 adaptive data analysis 的理论连接只停在动机层。噪声带 δ 假设评估噪声平稳——LLM-judge 的非平稳漂移未处理。
3. **Leakage critic 是启发式 LLM 审查**：显式背题拦得住，隐式泄漏（如通过风格适配 judge、间接编码任务分布）未必；论文只能靠确定性判分域旁证。
4. **超参数量不小**（T、k、δ、b_min/max、w、m、n_prune、β0/β1），虽声称只在 evolve 集上定且“考虑操作因素”，仍有手工回潮的空间，且跨域需重调。
5. **进化循环自身的总开销**（T 轮 × 多候选 × k 次试验 × 全 evolve 集）与最终推理节省的盈亏平衡未完整报告，复现门槛不低。
6. **多维质量任务的 reward 设计**：本文场景有较干净的单一分数；对质量多维的任务（恰恰包括翻译），单标量 S 会让进化钻空子——非补偿准则只是部分缓解。
7. 与权重训练的交互（先进化再微调、联合优化）、以及 RSI 本身的安全与可控性，均未触及。
