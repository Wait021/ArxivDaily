# Realtime-Venus 深度解读

> 一句话概括：这是一个“**全双工对话前端 + 异步工具后端**”的双循环系统——9B 前端模型在持续听/看/说的同时，通过私有自然语言委派通道把重计算任务交给后台 Harness 异步执行，结果在固定证据快照的前提下延迟重返会话。它的核心张力是：**实时交互和外部计算运行在完全不同的时间尺度上，且会话状态在工具执行期间会漂移**。

---

## 🎯 研究动机与要解决的问题

论文开篇点出的核心矛盾非常精确（Section 1）：

> “后台任务需要请求及其证据的**稳定记录**，但其结果必须在一个**执行期间可能已经改变的会话**中被解释。”

拆解为四个子问题：

1. **全双工时序控制**：用户在模型说话时发声，声学上相似的事件对应完全不同的会话功能——backchannel（“嗯嗯”，应继续说）、打断（应停止/修正/转向）、对他人说话（应无视）、背景音（应无视）。传统 VAD 触发的二元“停止/继续”无法区分这些。
2. **主动响应**：视频交互中，模型要自己判断“何时值得开口”（如裁判吹哨时提醒用户），而非等用户提问。
3. **异步委派**：语音会话中发起工具调用/深度推理，延迟数秒甚至更久才返回；期间用户可能打断、改需求、提出新问题。
4. **长会话上下文溢出**：小时级视频流 vs. 基座模型的有限滚动窗口。

值得注意的是，该团队明确选择用 **9B 小模型做前端**，把“超出前端能力的推理”外包给后端——这是一个“小模型编排 + 强后端执行”的立场，与翻译智能体“轻量路由器 + 专业翻译/QA 工具”的结构同构。

## 🔧 方法

### 1. 总体架构：双循环解耦（Section 3）

- **交互循环**（延迟敏感，持续运行）：前端模型流式感知 → 更新会话状态 → 决定 listen/speak/yield → 原生 Thinker-Talker 输出语音。
- **能力循环**（按需触发，时长不定）：前端的私有委派请求激活 Harness，执行工具/推理，把结果“打磨”成可朗读的回复送回原会话。

两循环的接口被严格定义：**任务包（带因果上下文边界）进，准备好的回复（绑定原会话）出**。

### 2. 模型层：统一流序列化（Section 4.3，本文最有技术含量的设计)

一切按 **1 秒 chunk** 对齐到共享因果时间线，三条逻辑流交错成单一 token 流：

- **用户流**：Whisper 音频特征（~10/s）+ SigLIP2 视觉特征（Omni 版），说话期间**不关闭**，保留重叠语音、停顿、视觉事件；
- **助手流**：前景文本 + S3 语音 token（~25/s）+ 可选的委派指令（纯文本）；
- **后台流**：异步、纯文本，结果作为**外部观察（external context）插入，而非预测目标**。

新增 7 个特殊 token：`<delegate>`/`</delegate>`（发起委派，对用户隐藏）、`<backend>`/`</backend>`（接收结果）、`<|listen|>`/`<|speak|>`/`<|turn_eos|>`（轮次控制）。

几个精妙之处：

- **自然语言委派而非结构化函数调用**：前端在 delegate span 里输出一段自包含的自然语言任务（“查询今天北京限行尾号及京牌尾号7能否通行”），由后端 agent 分解为一次或多次函数调用。前端**完全不需要编码后端工具 schema**。
- **说话中途可以追加委派**，不必关闭当前轮次；复合请求按语义顺序触发多次调用。
- **文本-语音背压调度**（式 2）：每个 chunk 根据已调度语音的播放进度 τ 与候选文本的预估时长，动态决定发射多少文本 token——播放滞后就少发文本，播放有余量就多发。
- **打断被建模为事件条件化的语义控制**（Section 4.4）：stop/reject（弃掉未播部分）、repair/update（吸收新证据、重生成未说出的续文）、redirect/follow-up（挂起当前计划转新请求）。**已播放的音频不可变，未说出的续文可修订**——这是共享语义状态带来的关键能力。

### 3. Harness：委派的生命周期管理（Section 5）

三阶段 + 状态机，这是对 Tool Use 研究者最有参考价值的部分：

- **Capture（因果任务捕获）**：委派请求完成时，用**时间戳围栏 + 序列围栏**从会话缓冲区构造证据快照 X_i——只允许请求开始前 T_i 时刻可得的观察进入，此后的任何观察（包括播放确认）**不能修改**该证据。请求身份校验保证一个请求至多创建一个工作项。
- **Dispatch（可扩展能力执行）**：能力注册表 C = {多模态能力， 通用能力} ∪ 技能集，每个能力带契约（合法输入 + 参数 schema）。路由器 R 做**一次基于模型的决策**，只看紧凑证据摘要 z_i 和请求元数据，**不检查原始媒体**；schema 校验失败则在执行前拒绝。
- **Return（会话式结果重返）**：适配器 A 对执行结果做一遍**纯文本 polishing**，剥离保留控制 token，包成单个 `<backend>` 私有消息送回原会话。**职责切分非常清晰：Harness 决定回复的内容与措辞，前端决定何时说出来**。
- **状态机**：`QUEUED→RUNNING→COMPLETED→DELIVERING→DELIVERED`（或 `FAILED`），区分“结果已备好”与“语音已实际播出”（DELIVERED 需前端生成完成 + 每个 Talker chunk 播放确认）。请求携带**新鲜度截止时间**，过期结果被排除出重返流程。

### 4. 免训练长视频记忆（Section 4.2）

即插即用、与微调策略解耦的三步：

- **门控**（写入哪些帧）：受 AdaCodec 预测编码启发，用块级运动补偿的预测残差估计视觉变化量，只归档“信息量足够”的帧，带短事件保护和最大连续丢弃约束；
- **检索**：MaxSim 式 token 级最大余弦匹配 + 用分数的 MAD（中位数绝对偏差）给“区分度高的 query token”加权 + MMR 式“相关性 × 新颖性”组合打分去冗余；
- **重组装**：检索帧 + 其邻近音频段 + 近期短窗口 + 当前查询按时间顺序拼成上下文。

### 5. 数据管线与训练配方（Section 4.5–4.6）

- **280 万样本、9 类**：离线理解 ~56%、主动双工 ~37%、委派工作流仅 ~6%；视频组 ~70%（仅 Omni 用），音频组 ~30%（两模型共享）。双工/委派数据合计约 72,200 会话 / 1,600 小时，中英各半，含 code-switching。
- **管线三阶段**：场景种子（设定/目标/语言/声学环境）→ 副语言与声学实现（犹豫、填充、笑声、重叠、背景说话人混合）→ 时间对齐与模型物化。**一条轨迹、两种物化**（audio-only / audio-visual），共享监督。
- **双目标监督**（Section 6.2）：每个事件同时标注 duplex target（continue/hold/yield/stop/revise）和 delegation target（retain/cancel/revise/reconcile/retry/fallback）。“意图稳定的中断可停播放但保留计算；意图改变的修正取消依赖工作并重规划。”
- **训练细节**：稀疏监督（只对 response span 计 loss）；**per-sample loss 归一化**（防长样本随 token 数主导 batch）；LM head 分 chunk 重计算以限制激活显存；**只训 Thinker，Talker 冻结**。

## 📊 实验与结果

**视频理解（在线模型中 6/8 最佳，表 2）**

| 基准 | RT-Venus-Omni | MiniCPM-o 4.5 (基座) | 最佳离线参考 Gemini-3.5-Flash |
|---|---|---|---|
| StreamingBench | **70.2** | 67.9 | 77.3 |
| OVO-Bench | **64.7** | 60.7 | 71.6 |
| ProactiveVideoQA | 46.2 | **47.5** | 56.5 |
| OmniPro | **29.0** | 25.6 | 52.4 |
| Daily-Omni | **81.3** | 79.4 | 82.3 |
| OmniVideoBench / LVOmniBench | **39.2 / 38.9** | 37.7 / 36.7 | 64.6 / 58.2 |

注意两点：ProactiveVideoQA 和 WorldSense 反而低于基座；离线大模型（尤其 Gemini-3.5-Flash）仍全面大幅领先——9B 在线的“最佳”是有严格限定的。

**记忆模块（表 3）**：RT-Venus-Omni +memory 在所有时长 bin 均提升，LVOmniBench 60–90 分钟段 +5.88 pt，LongVideoBench 40–60 分钟段 +4.76 pt；但同一模块给 MiniCPM-o 4.5 用时长视频段反而略降——**收益依赖基座**。

**音频（表 4/5）**：RT-Venus-Audio 拿下 MMAU 78.0、MMAU-Pro 63.2、Llama Questions 83.8、Speech CMMLU 67.8，AlpacaEval 4.81 并列第一；MMAR（65.6）和 TriviaQA（75.7）第二，均输给 30B-A3B 的 Qwen3-Omni。

**全双工 Full-Duplex-Bench v1.5（表 6，本文最强结果）**

| 场景 | RT-Venus-Audio | Gemini 3.1 Live | GPT-4o | Joy-Duplex |
|---|---|---|---|---|
| 打断响应率 C_RESPOND↑ | 0.75 | 0.77 | 0.78 | **0.88** |
| Backchannel 继续率↑ | **0.97** | 0.95 | 0.70 | 0.96 |
| 对他人说话 继续率↑ | 0.88 | 0.66 | 0.02 | 0.72 |
| 背景音 继续率↑ | **0.86** | 0.66 | 0.04 | 0.85 |

GPT-4o 的模式是“逢声必应”（背景音响应率 0.93），RT-Venus 的模式是“该继续时稳如磐石”——论文自己承认**强继续 ≠ 强打断处理**，打断响应率仍低于三个闭源/专用系统。

**工具使用 FDB-v3（表 7，关键短板）**

| 模型 | 工具选择 F1 | 参数准确率 | Pass@1 |
|---|---|---|---|
| GPT-Realtime | **87.6** | **68.0** | **60.0** |
| RT-Venus-Omni | 86.0 | 53.1 | 43.0 |
| RT-Venus-Audio | 82.0 | 52.2 | 42.0 |

选择 F1 几乎追平，但**参数准确率差 15 pt、端到端差 17 pt**——自然语言委派把“选对工具”变简单了，但“把口语中带犹豫/自我修正的约束落成正确参数”仍是硬伤。

**委派决策（内部基准，表 8）**：RT-Venus-Omni 总体 75.93%（召回 68.33% / 特异性 84.44%）；RT-Venus-Audio 总体 68.89%（召回 **92.22%** / 特异性 **39.44%**）。两个模型呈现**镜像失败模式**：Audio 版“什么都要委派”，Omni 版“该委派的漏掉”——这是全文对 Agent 研究最有诊断价值的一张表。

## ⚠️ 局限与开放问题

1. **参数落地是最大短板**：FDB-v3 上 53% 的参数准确率意味着近半数委派即使路由正确也无法正确执行；论文只提出“需要进一步检查执行轨迹”，没有给出方案。
2. **委派决策的两难未解**：召回与特异性此消彼长（同一训练配方、不同数据子集产生镜像失败），暗示 6% 的委派数据占比可能不够，或“该不该委派”本质上是模糊边界问题。
3. **无消融实验**：论文明确承认未隔离各训练组件贡献——双工数据、委派数据、记忆模块各自的因果贡献不清楚。
4. **委派基准是内部的**：只评“路由决策正确性”，不评“委派后执行与结果整合是否成功”，后者才是端到端难点。
5. **1 秒 chunk 粒度偏粗**（自认 future work）：短促事件与响应时机会被吞掉。
6. **闭源离线模型仍碾压**：Gemini-3.5-Flash 在几乎所有视频基准上领先 10–25 pt，“在线最佳”的成色需打折。
7. **结果重返的一致性问题只解决了一半**：证据边界固定了任务侧，但“结果返回时会话已漂移”只靠新鲜度截止粗暴丢弃，没有增量重规划/部分结果利用机制。
8. 合成数据占大头（1,600h 全为管线生成），真实嘈杂场景的分布外表现存疑。

## 💡 对我的研究的启发

这篇论文表面是语音交互，与文档翻译不同域，但它的**异步委派架构几乎每一层都可以平移到 PPT/XML 翻译智能体**：

**1. 双循环架构 → 翻译智能体的“编排前端 / 执行后端”分离。** 用户上传 PPT 后，轻量前端持续与用户对话（确认语言对、风格、术语偏好），重计算任务（百页文档翻译、图表 OCR、TM 检索）进后台队列异步执行——用户不必干等，还能中途追加指令。你的翻译 Agent 如果目前是“上传→阻塞→返回”的单循环，这是最直接的可借鉴架构。

**2. 证据快照 + 围栏 → 源文档版本固化。** Capture 阶段的“时间戳/序列围栏”机制可直接改造成：**翻译任务发起时对源文档、术语表、风格指南做版本快照**；工具执行期间用户编辑不污染任务；结果返回时做**新鲜度检查**（源文档 hash 变了→结果标记过期→只增量重译受影响 slide）。这解决了长文档翻译中“翻到一半用户改了源文件/术语表”的一致性问题——与论文的“会话漂移”问题同构。

**3. 私有 token 通道 → XML 流内嵌控制标记。** `<delegate>/<backend>` “模型可见、用户不可见、训练时不算 loss（后台结果只作条件不作预测目标）”的设计，正好对应 XML 翻译中的做法：在 XML 翻译流中嵌入 `<tool:term-query>`/`<tool:result>` 类私有标签，工具返回的术语/TM 参考作为上下文插入而非学习目标，最终导出时剥离。**backpressure 调度（式 2）也可平移**：根据下游写回/渲染速度调节各 slide 译文的生成节奏。

**4. 委派路由 + 两种失败模式 → 翻译元素路由的评估设计。** “哪些元素直接翻、哪些调工具（代码块→代码翻译器、图表→OCR+布局工具、术语→术语库）”就是翻译版的 delegate decision。论文的内部基准给了现成的评估框架：**recall（该调工具的调了）+ specificity（不该调的不调）+ 混合推理准确率**三分法，可直接建一个“XML 元素路由基准”——漏调工具=术语/代码错误风险，过度调工具=延迟与成本爆炸。表 8 的镜像失败提醒：这两个指标必须同时报告。

**5. 自然语言委派 + Harness 组装参数 → 规避小模型的参数幻觉。** 论文 53% 参数准确率的教训：与其让 LLM 从头生成结构化调用参数，不如让它输出自然语言子任务，由 Harness 的路由器**从结构化文档上下文自动组装参数**（slide ID、shape ID、语言对、术语表版本都来自 XML 解析结果，而非 LLM 生成）。对 PPT 翻译这尤其自然——文档本身就是强结构的，参数应该“查”出来而不是“编”出来。

**6. 状态机 → 多元素并行翻译的任务管理。** `QUEUED→RUNNING→COMPLETED→DELIVERING→DELIVERED` 映射为 `pending→translating→QA-passed→writing-back→committed`，其中 DELIVERED = 译文已写回文档（对应论文要求的“播放确认”）——区分“翻完了”和“已落盘”对用户可见性至关重要；异常按状态定位故障阶段（OCR 失败 vs 翻译失败 vs 写回冲突）。

**7. 免训练记忆模块 → 超长文档翻译一致性检索。** 几百页 PPT 超出窗口时，用其 relevance+novelty 检索“已翻片段 + 术语决策记录”作为当前 slide 的翻译上下文；**门控思想**（只存信息量大的帧）对应“只归档非模板页、跳过重复版式/目录页”。零训练、与微调解耦，适合作为你翻译 Agent 的即插即用一致性层。

**8. 打断三模式 → 增量翻译的中途改需求。** stop（弃掉未写回的译文草稿）/ repair（保留已导出部分、只重生成未提交部分）/ redirect（挂起当前 slide 转新指令）——“已播放音频不变、未说出续文可修订”直接对应“已写回用户文档的部分保持、未提交草稿按新术语表重生成”。

**9. 训练配方细节可直接抄。** 稀疏监督（XML 翻译训练中**只对译文 span 计 loss，不监督源结构 token**——防止模型学复制结构）；per-sample loss 归一化（防止超长 XML 样本主导 batch）；LM head 分 chunk 重计算（长文档样本训练省显存）。

**10. 数据管线的双目标轨迹。** 场景种子（文档类型/语言对/领域）→ 事件注入（术语冲突、用户中途改风格、工具失败重试）→ 物化成带结构标记的轨迹，且每个事件同时标注“翻译行为目标”和“工具管理目标”——这是构造翻译 Agent 训练轨迹（SFT 或后续 RL）的完整模板。

**不建议借鉴的部分**：其工具调用端到端能力本身（FDB-v3 落后 GPT-Realtime 17 pt）；以及若你的翻译 Agent 不涉及实时用户交互，全双工/打断部分可以整体跳过。

**相关度：⭐⭐⭐⭐（4 星）**——领域不重叠（实时语音/视频交互 vs. 文档翻译），其全双工核心与你无关；但异步委派架构（证据快照、私有 token 通道、路由-执行-重返状态机、自然语言委派模式）与你的 Agent/Tool Use 方向直接对口，记忆模块、数据管线和训练技巧对 PPT/XML 翻译智能体高度可迁移，属于“方法层强相关、任务层弱相关”的论文。
