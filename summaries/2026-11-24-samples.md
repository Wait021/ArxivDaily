## 阅读指引（基于下面三篇）

**排序（按对我的价值）**
1. Doc2FRC：正中文档级MT主线，分块/对齐算法与评测资产可直接复用，证据也最扎实。
2. A2HTrans：“分解—排序—修复—验证”流水线对富结构文档翻译迁移价值最大，但证据中等。
3. AppSci-Bench：契合Agent评测兴趣，但离翻译主线最远。

**关联**
前两篇确有呼应：都是先分块/分解再翻译并做对齐，都微调7B级模型；AppSci-Bench与前两者无实质关联，不硬凑。

**只读一篇：Doc2FRC**——最对口主线且证据最硬。可直接用于PPT/XML翻译智能体的做法：①固定区间切块＋训练/推理分块一致＋双边界对齐——“分块微调显著优于整篇微调”是论文结论，移植到PPT/XML是我的推断；②把A2HTrans的编译器反馈修复换成XML/schema校验驱动修复，属我的推断而非论文结论。

### [Doc2FRC: Length-Consistent Document-Level Machine Translation via Fixed-Range Chunking](http://arxiv.org/abs/2609.12674v1)

`2609.12674v1` · 2026-09-11 · [PDF](https://arxiv.org/pdf/2609.12674v1)

#### 概览
论文类型：方法为主（分块算法＋训练策略），数据集/基准为辅。论文用两阶段动态规划把任意长文档切成落在固定 token 区间（主实验 [256,512]）内的块，训练与推理使用同一分块方式以对齐长度分布，配合双边界匹配做源—目标块对齐，在两个 7B 基座上系统比较 D2DFT/STAIR/SEP/UNI 四类微调模型。最硬的一条证据（论文报告）：IWSLT2017 上，分块微调（SEP/STAIR-2c1t）对整篇微调和原模型的 d-BLEU 优势在两个基座、两个方向上均通过配对 bootstrap 检验（p≤1e-4，图 4）。我判断：在其实验设置内结果扎实，消融和显著性比同类工作全；但“固定区间”这一新颖组件相对普通定长窗口的净增益小且未做显著性检验，标题主张强于证据。

#### 问题与思路
- 要解决的问题：长上下文 LLM 直接 Doc2Doc 翻译易产生 n-gram 重复、随序列变长退化；分块翻译是通行解法，但训练与推理的块长度分布难以对齐（固定句数/固定窗口会在文末留下任意长的尾巴），而已有报告指出长度分布错配会拉低性能。
- 论文点名的旧做法与短板：Doc2Sent 用固定句数上下文（Wu 2024a、Li 2024），上下文信息不足；Ramos et al. (2025) 把文档切成固定份数混合训练，保证不了长度分布对齐；Peng et al. (2025a) 改位置编码（UnifPE 等）走跨长度泛化路线；FW（定长滑窗）有尾部短块问题。
- 核心直觉：与其让模型泛化到任意长度，把训练和推理的输入都映射进同一长度区间、只在该分布上训练。走一遍：输入一篇约 2000 token 的英文文档；Stanza 切句为基本单元；DP 第一阶段搜索每块长度严格落在 [256,512] 的最小代价划分（代价为偏离区间中心的平方），不可行时允许至多 K=8 块越界，得到如 5 个块；目标端用双边界匹配（源块首尾单元与目标单元算 LaBSE 余弦×位置高斯先验的混合分，DP 取单调最优路径）划出对应目标块；按 0c1t/1c1t/2c1t/FS4 格式构造训练样本，或整篇训练 D2DFT；推理对测试文档执行同一 FRC，逐块翻译（默认 source-only 上下文，各块可并行）。

#### 最脆弱的一环
FRC 相对 FW 的净增益。论文的标题级卖点是“固定区间带来的长度一致性”，但表1 的大额提升（对 D2DFT、原模型）任何分块格式都能获得（论文也写明 chunking generally outperforms d2d），固定区间独有部分只剩表4 中不超过约 1.5 点 d-BLEU、约 1.0–1.4 点 GEMBA-DA 的差，无显著性检验、单种子，且在 OOD 上归零。若这部分是噪声，方法贡献就退化为对 Ramos 式分块训练的系统化工程化，“FRC 是关键”的主要结论随之动摇。最小检验：对 FRC/FW/FN 各训 3 个随机种子、做配对 bootstrap，并补 1–2 个 OOD 测试集。

#### 边界
**作者承认的局限**（Limitations 节）：GuoFeng 测试集与 DocBlocks 训练数据部分重叠，故弃用其评测；Ramos et al. 模型未公开，只能比相对增益、不等价；FRC vs FW/FN 的中间处理（对齐、过滤）不同，SEP 设定可能同质化掩盖差异；上下文选择留作未来工作；因全参微调成本，多数分析在单基座单设定下完成。

**我的质疑**：
1. GlobVDoc 预训练污染风险（§4）：论文只保证与 DocBlocks 五源独立；Global Voices 属 OPUS，Qwen/GPT-4.1/Gemini 的预训练语料可能包含这些已发表的人工译文。影响：表2 中商业模型与微调模型的对比可信度、“OOD”的措辞外推。把握：中。
2. GEMBA-DA 的 judge 是 GPT-4.1，而 GPT-4.1 同时是被评系统（§5.1.2、表1/2）：自偏好风险；FRC 对 FW 最清晰的优势恰落在该指标（§6.2），单一 judge、温度 0，未报告一致性。影响：以 GEMBA-DA 支撑的结论（含 FRC 优势）打折。把握：中。
3. GlobVDoc 选文偏置（附录C 准则 3/4）：剔除句对齐缺口大、语序重排的译文，等于选择了对分块管线友好的文档。影响：OOD 结论对“结构自然重排的真实文档”外推受限。把握：中高（准则为明文）。

#### 对我的价值
论文本身的发现（对方向①直接可用）：
- GlobVDoc（90 篇、9 个目标语向、严格句对齐、附完整文档元数据）可作文档级评测的 OOD 补充测试集；表2 给出 GRAFT/DELTA 翻译 agent 与微调 7B、GPT-4.1-mini 横评——7B 微调在 OOD 仍输 GPT-4.1-mini 约 2.6 点 d-BLEU（换算：44.65−42.06），是“微调路线 vs agent 路线”的量化参考点。
- FRC 的 DP 定长切块与双边界对齐可直接搬进长文档翻译 agent 的预处理/工具层；表6 的 LoRA 三适配器方案给出部署权衡样本（GlobVDoc 上 LoRA 1c1t 43.28 高于全参 41.87）。
- 附录G 的上下文策略实验（source-only 可并行、NRR 低；source+MT 术语一致性升但时延约 2.5 倍、错误传播率 89%（17/19））对翻译 agent“是否回填已译上下文”的设计决策有直接参考价值。
- 评测实现可复用：d-COMET 三种切块取平均的 SLIDE 式流程、LTCR 参考侧单语对齐变体。
- 方向②③与本文无实质关联，不强行迁移。

我的推断：
- PPT/XML 展平后的“结构标记＋正文”混合流同样可按 token 区间做 DP 切块，在保留结构骨架的同时控制单次送入模型的长度；FRC 可作为翻译 agent 的工具层组件，与是否微调解耦。
- GlobVDoc 每语向仅 10 篇，适合做 OOD 抽查，不宜当主评测集。

#### 结论
值得精读。对文档级 MT 评测与翻译 agent 方向，其数据集、切块/对齐算法、评测变体和 agent 对比数字都有直接复用价值；方法本身的新颖增量（固定区间对普通窗口）证据偏弱，阅读重心应放在实验设计与评测资产上。

### [Beyond Code Translation: Agentic Android-to-HarmonyOS Migration](http://arxiv.org/abs/2611.11192v1)

`2611.11192v1` · 2026-11-08 · [PDF](https://arxiv.org/pdf/2611.11192v1)

#### 概览
论文类型：方法/系统论文（提出 A2HTrans 智能体框架），附带小规模实证评估与错误分类分析。该文把 Android→HarmonyOS 应用迁移从“逐文件代码翻译”重构为“功能感知分解 + 依赖排序翻译 + 编译器与小模型修复 + LLM 语义对齐验证”的智能体流水线，并用 1,752 对官方文档“规格—代码”对微调 7B–16B 模型修 ArkTS 语法。最过硬的证据：在 14 个真实 Android 应用、同一驱动模型（正文为 Claude-Sonnet-4.5）下，五个 0–100 人工指标平均分全面高于 prompt 基线与 Claude Code CLI（Table II）。我判断：工程设计与错误分析有价值，但核心结论全部依赖作者自评、无消融、文本多处自相矛盾，总体可信度中等。

#### 问题与思路
- 要解决的问题与动机：2021 年起华为手机改用 HarmonyOS，应用生态需要存量 Android 应用迁移；两平台在语言（Java/Kotlin 对 ArkTS）、UI 框架（View 体系对 ArkUI 声明式）、权限模型、生命周期、API 上差异大；ArkTS 公开语料少，LLM 直接生成常出语法错误；迁移产物缺乏测试，难以自动验证（第 I、II 节）。
- 论文自己对比的先前做法：TransAgent、AlphaTrans、RepoAgent 等仓库级 LLM 翻译聚焦方法/文件级转换、面向 Rust/C/C++ 等主流语言（第 II-B 节）；Wang et al. 的 A2H 只做 Android XML 布局到 ArkUI 的 UI 片段转换；Zeng et al. 手工分析 Android→iOS 迁移 bug，聚焦语法层。作者称端到端迁移引入的语义错配、资源配置、平台配置问题此前未被研究。
- 核心直觉：迁移是架构适配问题，需要“翻译合同”和形式化 oracle。具体走一遍（andOTP，71 个 Java 文件）：Step 1 静态分析产出组件/类/方法三级依赖图 → Step 2 用 Claude-Sonnet-4.5 自底向上摘要出功能清单（令牌列表、扫码添加、图片导入、手动录入等）→ Step 3 按依赖从少到多排序翻译单元（作者称依赖多的先翻会诱导 LLM 幻觉出缺失接口）→ Step 4 按 ArkTS 模板生成工程脚手架 → Step 5 官方编译器诊断喂给微调 DeepSeek-16B 修语法（至多三轮）→ Step 6 LLM 裁判对照功能规格打对齐分，低于 80% 触发修复（至多三轮）→ 输出工程并留人工复核。图 3 案例显示：prompt 基线丢掉三个添加入口，Claude Code 只剩手动录入，A2HTrans 保住全部三个。

#### 最脆弱的一环
RQ2 的全部结论建立在作者人工评分上：评分者即系统构建者（非盲），论文对评审人数自相矛盾（第 I 节"two reviewers"、V-B 节"three participants"、VII 节"three developers"），未报告评分者间一致性与显著性；摘要写 Claude-Sonnet-4.6、正文三处写 Claude-Sonnet-4.5，模型版本也对不上。8% 量级的组间差距若遇上评分偏差或噪声即可能不成立。最小检验：将三个系统的输出匿名后交由未参与开发的 2–3 名评审按同一 rubric 重打分，报告 Krippendorff's alpha 与配对显著性。

#### 边界
**作者承认的局限**：14 个样本不代表大规模工业系统与复杂后端集成；结果依赖所用 LLM 与工具配置（VII）；微调数据仅官方文档，覆盖不了真实 ArkTS 开发多样性（VII）；人工评测存在主观性（VII）；实验排除了重度依赖平台第三方库（如 Google Play Services）和 Kotlin 的项目（IV-B3），且该节正文写“ten”个应用与 Table I 的 14 个矛盾。
**我的质疑**：
1. 上述三处文本矛盾（评审人数、应用数量、模型版本），来源为摘要/第 I、IV、V、VII 节互对；直接影响核心评测可信度。把握：高，纯文本可查。
2. 无任何消融。prompt 基线也带编译修复循环，增益究竟来自功能引导、依赖排序、语义验证还是更深的迭代轮数，无法归因。影响想复用设计的人。把握：高。
3. 逐项目并不占优：Osmand 上 Claude Code 的 completeness/correctness 为 82.5/77.5，A2HTrans 为 72.5/70.0；AntennaPod 上 A2HTrans 耗时 18.43 分钟，Claude Code 16.49 分钟（Table II）。优势随项目类型变化，论文未分析失效条件。把握：高。
4. 语义验证的裁判与翻译用同一个 Claude-Sonnet-4.5，存在自我偏好风险；80% 阈值与三轮上限无消融。把握：中。

#### 对我的价值
论文本身的发现（对翻译智能体方向）：依赖从少到多的翻译排序可减少级联幻觉（III-B3）；编译器/解析器类形式化工具当 oracle、微调小模型做定点修复，优于让大模型自查；低资源目标语言可用官方文档“规格—实现”对做指令微调，1,752 对就把 pass@1 从约 0.22 提到约 0.68（V-A）；Table III 的错误分类（scope contraction、scaffold 约束、平台 API 缺口等）可直接对照富结构文档翻译的失败模式；作者明确指出缺乏跨系统自动化行为评测是该领域瓶颈（VI）。
我的推断：对 PPT/XML 富结构文档翻译智能体，可迁移三件事——把编译器换成 schema 校验或渲染检查器做工具验证；按结构依赖排序翻译（先母版样式后内容页）；用目标格式的官方规范–样例对微调小模型修格式错误。其人工评测的反面教训（人数不一致、无一致性系数）提醒我自己的评测协议要报告评分者信息与一致性。对生物智能体与教学智能体两个方向，本文没有直接可用的内容，仅有“形式化约束检查 + LLM 修复循环”这一通用智能体技巧上的同构，算不上论文贡献。

#### 结论
值得浏览。流程设计、错误分类学和低资源微调配方对翻译智能体研究有参考价值，但作者自评、无消融与多处文本矛盾使其证据强度不足以支撑精读或照搬结论；重点读第 III、IV-D、VI 节即可。

### [AppSci-Bench: Can LLMs Build AI Agents and Make Them Better?](http://arxiv.org/abs/2611.25360v1)

`2611.25360v1` · 2026-11-19 · [PDF](https://arxiv.org/pdf/2611.25360v1)

#### 概览
论文类型：基准论文为主，附带实证评测。做法：让 LLM 扮演"应用科学家"，先向一个掌握隐藏需求的模拟客户提问引导需求，再在沙盒业务环境里写代码构建并部署一个 artifact agent，最后用构建期不可见的新数据在保留测试套件上只评这个 artifact；主指标 MMS@k（对每个评测样本取 k 次独立构建的最低分再平均）。最过硬的一条证据是 Table 2/Table 6 的七个模型跨四种 harness 设置的全量结果，配合附录 H 的分层置换检验与附录 L 的防泄漏流程。总体判断：构造认真、自我批评充分的工业界基准，"agent-building 存在大量 headroom"的定性结论可靠；但 headline 数字（59.1%）和模型排序要按"每模型各取最优设置、原生 harness 不受预算约束"打折读。

#### 问题与思路
- 要解决的问题：已有基准测的是"被构建好的 agent"（工具调用、SWE、网页操作、τ-bench 类对话策略），不测"构建 agent 的过程"。LLM 越来越多地被用来搭系统，这个能力缺少直接测量。这决定了"agent 自动生产 agent"的现实边界，也是企业真实工作流。
- 论文自己对比的两类做法：(1) agent 行为基准（τ-bench/τ²-bench、CRMArena、SWE-bench 等）——被测 agent 已存在，产出它的过程不被评；(2) 自动 agent 设计（DSPy 系 prompt 优化、ADAS、MASS）——假设任务和目标函数已经给定。并发工作 ττ-Bench 同样做端到端构建，AppSci 的差异是把需求引导率与自建内部基准的质量变成显式评测对象，并新增五个领域。
- 核心直觉：把"构建"拆成可分离的子能力（引导、探索、实现、自评、改进），逐一量测，最终只评 artifact。用 Slides 任务（B.1）走一遍：构建期 builder 只拿到一份非评测用途的样例请求加 KPI 文档；它问模拟客户"deck 最多多少页"，客户答"最多 40 页"；经 mini-SWE 子代理写代码、deploy_artifact 部署，可选地用 eval_generator 自建内部基准、optimize_agent 爬山优化；提交后换 10 个全新样本（五个产品虚构加五个 Zenodo10K 模板配 CERN/SEC 公开文档），按 11 个加权目标打分（3 项确定性检查、6 项 LLM judge、2 项视觉 judge，如模板遵循 0.75、groundedness 2.0），同时记录引导率、自评保真度、安全等过程分。
